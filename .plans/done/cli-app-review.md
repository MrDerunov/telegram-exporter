## Безопасность (1–6)

### 1. Хранение и передача секретов (api_hash, session, токены). Риски утечки в CI/CD
**Оценка: ⚠️**

План предусматривает цепочку SecretProvider и отделение секретов от конфига — это правильно. Но для CI/CD предлагается `.env` с session string в plaintext. Риск: `.env` может быть случайно закоммичен; CI/CD-логи могут содержать переменные окружения. Нет упоминания CI-специфичных secrets-менеджеров (GitHub Secrets, GitLab CI Variables).

**Рекомендация:** Добавить раздел «CI/CD Secrets» с рекомендацией использовать нативные secrets-менеджеры CI, а не `.env`. В коде — поддержка `TG_EXPORTER_SESSION_FILE` (путь к файлу с сессией) как альтернатива env var.

---

### 2. Безопасность SecretProvider. Порядок чтения/записи в цепочке
**Оценка: ⚠️**

Чтение: env vars → `.env` → keyring. Логично, env vars переопределяют файл.
Запись: **во все провайдеры цепочки**. Это опасно — `set()` для session string запишет её и в `.env`-файл (plaintext), и в keyring. Пользователь может не ожидать, что сессия окажется на диске.

**Рекомендация:** Разделить поведение: `set()` пишет только в первый доступный для записи провайдер (keyring), а запись в `.env` сделать явной опцией (`--export-session-to-env`). Или ввести флаг `writable` в каждом провайдере и писать только в writable.

---

### 3. Секреты в логах, stdout, конфиг-файлах
**Оценка: ✅**

ARCHITECTURE.md явно описывает редактирование секретов логгером. Конфиг-файл не содержит секретов. План не упоминает redaction в CLI-выводе, но это наследуется из core-логгера. Достаточно.

---

### 4. Права на конфиг и файлы экспорта в разных ОС
**Оценка: ⚠️**

ARCHITECTURE.md: конфиг — `0o600` на Unix. Но:
- Экспортированные файлы (чаты, медиа) — права не оговорены
- `.env` — упомянут `0o600`, но не в плане CLI, а в ARCHITECTURE.md
- Windows — `0o600` не применяется, нужен Windows ACL или `win32security`

**Рекомендация:** Добавить в план пункт «Безопасность файлов»: экспорт-директория — `0o700`, `.env` — `0o600`, на Windows — restricted ACL. В коде — хелпер `secure_permissions(path)`, платформозависимый.

---

### 5. Риски при хранении сессии в .env файлах
**Оценка: ❌**

Сессия в `.env` — это полный доступ к аккаунту Telegram. В плане это основной способ для CI/CD. `.env` легко утекает (коммит, backup, передача). Session string должна быть вне файловой системы где возможно.

**Рекомендация (критично):**
1. По умолчанию НИКОГДА не писать session в `.env`. Только keyring.
2. Добавить команду `tg-exporter auth export-session` — явный экспорт сессии (с предупреждением в stdout).
3. Для CI/CD рекомендовать env vars, установленные через CI secrets manager, а не `.env` файл.
4. В документации — красное предупреждение о рисках session в файлах.

---

### 6. Неинтерактивный режим (CI/CD) — безопасность
**Оценка: ⚠️**

Неинтерактивный режим работает только с предварительно сохранённой сессией. Это правильный подход (нельзя залогиниться без интеракции). Но:
- Нет валидации, что сессия валидна, до попытки экспорта
- Нет таймаута/обновления сессии (сессии Telethon протухают)

**Рекомендация:** Добавить `tg-exporter auth verify` — проверка валидности сессии без интеракции. В CI/CD вызывать перед экспортом. При протухшей сессии — понятная ошибка с инструкцией.

## Полнота (7–10)

### 7. Каких команд или опций не хватает
**Оценка: ⚠️**

Отсутствуют:
- `export --resume` — продолжить прерванный экспорт
- `export --message-types text|media|pinned` — фильтр по типам
- `export --exclude-media-types photo|video|...` — исключить типы медиа
- `export --all` — экспортировать все чаты из конфига одной командой
- `tg-exporter version` — версия утилиты
- `tg-exporter doctor` — диагностика (проверка конфига, keyring, сессии)

**Рекомендация:** Добавить в Фазу 3. Как минимум `version`, `doctor` и `--resume` — критические для реальной эксплуатации.

---

### 8. Какие сценарии использования не покрыты
**Оценка: ⚠️**

- Массовый экспорт всех чатов (без скрипта-обёртки)
- Экспорт в реальном времени (стриминг новых сообщений)
- Экспорт конкретного диапазона ID сообщений (не только даты)
- Экспорт с фильтрацией по автору

**Рекомендация:** Для MVP достаточно, но задокументировать ограничения. Массовый экспорт и фильтр по автору — кандидаты на v1.1.

---

### 9. Что должно быть в конфиг-файле, но отсутствует
**Оценка: ⚠️**

- Настройки по умолчанию для конкретных чатов (разный формат для разных чатов)
- `date_from`/`date_to` по умолчанию (для cron-задач)
- `retry_count`, `retry_delay` — настройки устойчивости к сбоям
- `rate_limit_pause` — пауза между запросами

**Рекомендация:** Добавить секцию `defaults.date_from`, `defaults.retry`, `defaults.rate_limit`. Чат-специфичные настройки — в v1.1.

### 10. Хватает ли CLI-команд для управления приложением
**Оценка: ⚠️**

Базовый набор (auth, export, chats, profile, config) покрывает основной сценарий. Не хватает:
- `version` — показать версию
- `doctor` — диагностика окружения
- `cleanup` — удаление старых сессий, временных файлов, кэша

**Рекомендация:** `version` — в Фазу 1, `doctor` — в Фазу 4.

## Обработка ошибок и edge cases (15–20)

### 15. Сетевые сбои во время экспорта
**Оценка: ❌**

План не упоминает retry-логику, таймауты, обработку ошибок сети. Telethon имеет встроенные реконнекты, но:
- Что происходит с частично скачанным медиа при обрыве?
- Сколько ретраев перед падением?
- Сохраняется ли прогресс для возобновления?

**Рекомендация (критично):** Добавить в план:
1. retry с экспоненциальной задержкой для сетевых операций (3–5 попыток)
2. Атомарную запись медиафайлов (tmp + rename)
3. Сохранение прогресса каждые N сообщений для `--resume`

---

### 16. Нехватка места на диске
**Оценка: ❌**

Полностью отсутствует. При экспорте канала с гигабайтами медиа диск может заполниться, и экспорт упадёт с невнятной ошибкой.

**Рекомендация (критично):**
1. Перед экспортом — оценка размера (хотя бы по количеству медиа-сообщений × средний размер)
2. В процессе — проверка `disk_free` после каждых N медиафайлов.
3. При нехватке — остановка с понятной ошибкой и сохранением прогресса.

---

### 17. Конфликты конфигурации (--date-from + --days)
**Оценка: ⚠️**

План не описывает, что будет при одновременном указании `--date-from` и `--days`. Click позволяет сделать их взаимоисключающими через `cls=MutuallyExclusiveOption`, но это не упомянуто.

**Рекомендация:** Добавить валидацию в команду export:
- `--date-from` / `--date-to` vs `--days` → взаимоисключающие
- `--last` vs любые фильтры по дате → взаимоисключающие
- При конфликте — понятная ошибка, а не молчаливое игнорирование

---

### 18. Несовместимые комбинации флагов
**Оценка: ⚠️**

Аналогично п.17. Дополнительно:
- `--transcribe` без `--download-media` → транскрипция невозможна без медиа
- `--analytics` при `--last N` → бессмысленно, но не задокументировано

**Рекомендация:** Систематическая таблица совместимости флагов в плане. Click валидаторы на каждую конфликтную пару.

---

### 19. Прерванный экспорт (Ctrl+C, kill)
**Оценка: ⚠️**

План упоминает `CancellationToken` и cooperative cancellation — хорошо. Но:
- Нет описания, как выглядит частичный результат (файлы обрываются на полуслове? JSON валиден?)
- Нет `--resume`
- Интеграционный тест «частичный результат валиден» упомянут, но без деталей реализации

**Рекомендация:**
1. Атомарная запись: писать во временный файл, переименовывать при завершении
2. Markdown-файлы дописывать с маркером незавершённости, убирать при завершении
3. При Ctrl+C — сохранить `export_history.json` с флагом `"interrupted": true`

---

### 20. Удаление/блокировка чата между экспортами
**Оценка: ❌**

Не упомянуто. Если чат удалён или пользователь заблокирован между запусками:
- `iter_messages` выбросит исключение
- `export_history.json` останется с прошлым `last_message_id`
- При следующем запуске — повторная ошибка без понятного сообщения

**Рекомендация (критично):**
1. Обработка `ChatNotFound` / `ChannelPrivate` — понятная ошибка пользователю
2. Опция `--skip-unavailable` для пакетного экспорта
3. Сохранение статуса чата в `export_history.json` (`"status": "unavailable"`)

## Операционные вопросы (24–28)

### 24. Логирование — что, куда, уровни
**Оценка: ⚠️**

План: уровень в конфиге, `--quiet`/`--verbose`, файл лога. Не хватает:
- Ротация логов (maxBytes, backupCount)
- Логирование в stdout vs stderr (сейчас неясно)
- Structured logging (JSON) для CI/CD

**Рекомендация:** Добавить в конфиг `logging.rotation` и `logging.max_size_mb`. `--quiet` → только stderr, обычный режим → info в stderr, `--verbose` → debug в stderr. Файл — всегда всё.

---

### 25. Обновление версий. Миграция конфига/профилей
**Оценка: ❌**

Полностью отсутствует. При обновлении с v1.0 на v1.1 структура `cli_config.yaml` может измениться, и старый конфиг станет невалидным.

**Рекомендация (критично):**
1. Поле `version` в `cli_config.yaml` и `profiles.json`
2. Функция `migrate_config()` с цепочкой миграций (1.1→1.2, 1.2→1.3)
3. При запуске — авто-миграция с предупреждением, либо `tg-exporter config migrate`
4. Бэкап старого конфига перед миграцией

---

### 26. Пакетирование — PyPI? Single binary?
**Оценка: ⚠️**

Фаза 5 упоминает «PyPI package, single binary?» — нужна конкретика. Для CLI-утилиты:
- PyPI — хорошо для Python-разработчиков
- Single binary (PyInstaller/Nuitka) — необходимо для пользователей без Python
- Docker image — альтернатива для изоляции

**Рекомендация:** Определиться в плане:
- Основной способ: `pip install tg-exporter`
- Single binary: PyInstaller, сборка в CI на все 3 платформы
- Docker: `Dockerfile` с предустановленной утилитой

Python 3.11+ явно указан. Платформы: macOS, Windows, Linux. Библиотеки (`telethon`, `keyring`, `faster-whisper`) кроссплатформенны.

**Рекомендация:** Добавить CI-матрицу (`ubuntu-latest`, `macos-latest`, `windows-latest`) × (`3.11`, `3.12`, `3.13`).

### 28. Rate limiting / throttling Telegram API
**Оценка: ⚠️**

Не упомянуто. Telethon имеет встроенный flood control, но при агрессивном экспорте:
- Можно получить `FloodWaitError` (до нескольких часов)
- При экспорте медиа — много запросов подряд

**Рекомендация:**
1. Добавить `--throttle` опцию (пауза между запросами в секундах)
2. По умолчанию — консервативная пауза (0.5–1с между download_media)
3. Обработка `FloodWaitError` с человеческим сообщением («ждите N секунд»)
4. В конфиг: `rate_limit.media_download_delay_ms`

## 🔴 Критические проблемы (нельзя пропускать при реализации)

1. **Сессия в .env (п.5)** — plaintext-сессия на диске. Решение: keyring по умолчанию, явный экспорт сессии с предупреждением.
2. **Сетевые сбои (п.15)** — нет retry, нет сохранения прогресса. Решение: retry + периодическое сохранение состояния + `--resume`.
3. **Нехватка места на диске (п.16)** — молчаливое падение. Решение: проверка свободного места до и во время экспорта.
4. **Удалённый/заблокированный чат (п.20)** — невнятная ошибка. Решение: обработка `ChatNotFound` с понятным сообщением, статус в export_history.
5. **Миграция версий (п.25)** — сломанный конфиг при обновлении. Решение: версионирование конфига + цепочка миграций + бэкап.
